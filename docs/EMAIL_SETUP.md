# Transactional Email Setup

Identity uses Stalwart over SMTP for transactional email. `log` is for
development only. Mailpit is useful for local UI tests, but a message accepted
by Mailpit is not proof of delivery by Stalwart or an external provider.

## SMTP settings

Configure these values for Identity:

```dotenv
MAIL_PROVIDER=smtp
SMTP_ADDR=stalwart:587
SMTP_HOST=mail.example.com
SMTP_TLS_MODE=starttls
SMTP_USERNAME=noreply@example.com
SMTP_PASSWORD=<secret>
SMTP_FROM=noreply@example.com
```

`SMTP_TLS_MODE` is `none`, `starttls`, or `tls`. `starttls` is the recommended
mode on port 587; `tls` is for implicit TLS, commonly port 465. Production
Identity rejects `none` when SMTP is the selected provider. With SMTP selected,
`GET /readyz` performs EHLO and authenticates without sending a message. The
SMTP error response code/text and recipient domain are logged; passwords are
never logged.

Optional platform-mail failover is configured only with both
`PLATFORM_RESEND_API_KEY` and `PLATFORM_FROM_EMAIL`. When either is unset,
Identity uses Stalwart only. Campaign delivery never uses this fallback.

## Local Stalwart

Compose pins the Stalwart image by digest and exposes the admin API, SMTP, and
submission ports on loopback. Provisioning uses Stalwart's JMAP management API;
it does not require `stalwart-cli` or a manual setup wizard. The script is
loopback-only and idempotently performs first-run setup, configures the domain,
creates `noreply`, and enables authenticated STARTTLS submission on port 587:

```sh
export STALWART_DOMAIN=sendwise.test
export STALWART_HOSTNAME=mail.sendwise.test
export STALWART_ADMIN_USERNAME=admin
export STALWART_ADMIN_PASSWORD='<local administrator password>'
export STALWART_SUBMIT_USERNAME=noreply
export STALWART_SUBMIT_PASSWORD='<local submission password>'
./scripts/provision-stalwart.sh
```

Use unique administrator and submission passwords outside disposable local
development. Keep both out of source control and logs. Compose receives the
recovery-admin credential only for local setup; the provisioner stores no
credentials in the repository. It validates STARTTLS on port 587 after
restarting Stalwart to activate the listener.

To route Identity through this local service, configure its environment as
follows (the host name must match a certificate trusted by Identity):

```dotenv
MAIL_PROVIDER=smtp
SMTP_ADDR=stalwart:587
SMTP_HOST=mail.sendwise.test
SMTP_TLS_MODE=starttls
SMTP_USERNAME=noreply@sendwise.test
SMTP_PASSWORD=<same submission password>
SMTP_FROM=noreply@sendwise.test
```

The local Stalwart integration test registers an account through Identity,
probes SMTP EHLO/STARTTLS/AUTH, sends the verification mail, then reads it from
the Stalwart inbox over JMAP. Its generated local certificate is pinned only by
that test; production SMTP continues to verify the configured host using the
system certificate roots.

## DNS and outbound mail

For a public mail domain, configure and verify the following with the DNS
provider:

1. **MX:** `example.com MX 10 mail.example.com.`
2. **Host address:** `mail.example.com A <server IPv4>` and, if used,
   `AAAA <server IPv6>`.
3. **SPF:** publish one SPF TXT record, for example
   `v=spf1 mx -all`. If another relay sends mail for the domain, include that
   provider's documented mechanism instead of publishing a second SPF record.
4. **DKIM:** publish the selector and public key generated by Stalwart for the
   domain. Confirm the selector matches the active signing key.
5. **DMARC:** start with a monitoring policy such as
   `v=DMARC1; p=none; rua=mailto:dmarc@example.com`, review reports, then move
   toward `quarantine` or `reject` only after all legitimate senders align.

Set reverse DNS/PTR for the sending IP to `mail.example.com`, and ensure the
hostname resolves back to the same IP (forward-confirmed reverse DNS). Ask the
hosting provider whether outbound TCP port 25 is allowed. From the sending
host, check a remote MX on port 25, for example:

```sh
nc -vz gmail-smtp-in.l.google.com 25
```

Also verify that inbound port 25 is reachable when Stalwart is expected to
receive mail. A successful local SMTP submission test proves only that the
application handed the message to the relay; it does not prove external
delivery, inbox placement, or reputation.

After the local Identity service is configured, run
`scripts/smoke-mail.sh <recipient>` with a new, unregistered mailbox. It creates
an unverified smoke-test account and reports whether the configured relay
accepted its verification message. During deployment, set
`DEPLOY_SMOKE_MAIL_TO` to opt into this check; it is skipped when unset. The
smoke test is restricted to a loopback Identity URL and does not claim inbox
delivery. Since the smoke account remains unverified, use a fresh recipient for
each run and unset `DEPLOY_SMOKE_MAIL_TO` after the one-time deployment check.
